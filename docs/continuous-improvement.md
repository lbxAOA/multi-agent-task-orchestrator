# 持续优化机制

本 Skill 是可验证的团队运行手册，不是不断堆叠的提示词。复盘是可选的维护工具，不是每个任务的强制步骤。只有在需要时记录真实证据，才能用于改进委派、调度和验收规则。

## 何时复盘

以下情况可以创建复盘：

- 用户明确要求复盘；
- 任务契约明确启用复盘；
- 用户提供历史复盘并要求据此改进 Skill；
- Hermes 判断任务中的失败、返工、冲突、高风险问题或经验具有明显复用价值，并在当前任务中获得允许。

未经明确启用，Hermes 不自动创建复盘文件。未创建复盘不影响任务完成判定，也不得在报告中声称复盘已经生成。

## 按需复盘流程

启用复盘后：

1. **收集证据**：保存任务契约、执行通道、任务单、修改范围、验收命令、退出状态和 A2A `context_id`（如有）。
2. **创建记录**：从 `retrospective-template.md` 创建 `docs/retrospectives/YYYY-MM-DD-<简短-kebab-case-任务名>.md`；同名文件追加序号，不覆盖历史。
3. **只写事实**：明确成功、失败、返工、冲突、超时和未验证项；没有运行的测试必须写明“未运行”及原因。
4. **提出候选规则**：每条候选规则必须包含“触发条件 → Hermes 动作 → 验收标准”。
5. **筛选规则**：仅在同类问题至少两次出现、单次造成明显风险，或用户明确要求改变行为时，才写入主 Skill。
6. **最小改动**：优先精确更新 `SKILL.md`，删除被替代的规则，避免重复和无关重写。
7. **验证与版本化**：在下一次匹配任务中验证新规则；更新 frontmatter 版本和 `CHANGELOG.md` 后再发布。

## 候选规则质量门槛

规则必须同时满足：

- **可触发**：明确何时适用。
- **可执行**：说明 Hermes 要做什么，不使用“注意”“尽量”等模糊词。
- **可验证**：能由 diff、测试、委派记录、A2A 回复或退出码验证。
- **通用**：不把单个仓库的临时目录、依赖版本或命令写进主 Skill。
- **不重复**：已有规则可覆盖时，补强原规则而非新增近义句。

## 版本策略

- `0.3.x`：重命名、规则澄清、模板或记录机制的小修正。
- `0.4.0`：新增一个完整流程模块，例如 worktree 生命周期或失败恢复状态机。
- `0.5.0`：引入经过样本验证的任务路由指标或持久化协作机制。
- `1.0.0`：在多个不同仓库和任务类型中验证后，核心流程保持稳定。

## 迭代重点

1. **证据化交付**：统一成员交付格式，强制记录实际命令和退出码。
2. **隔离并行**：完善 worktree 创建、命名、清理、合并与冲突恢复。
3. **路由校准**：有足够的按需复盘样本后，根据返工率、测试通过率、超时率和审查发现数调整通道选择；不依据一次成功或失败下结论。
4. **持久化协作**：只有跨会话、跨仓库或任务依赖复杂时，再考虑 Hermes Kanban 或计划文件。

## 维护原则

复盘记录是可选的项目维护产物，不是运行时必需文件。保留模板和历史记录，但不要为了填表而给简单任务增加流程负担。
