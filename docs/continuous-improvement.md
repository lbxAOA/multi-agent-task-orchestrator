# 持续优化机制

本仓库把 Skill 当作可验证的团队运行手册，而不是不断堆叠的提示词。优化必须来自真实任务的证据，并通过版本化变更交付。

## 核心循环

每个使用该 Skill 的 A2A 团队任务结束后，执行：

1. **收集证据**：保存任务契约、各 peer 的任务单与 `context_id`、修改范围、验收命令及真实退出状态。
2. **填写复盘**：从 `retrospective-template.md` 创建一条记录，明确成功、失败、返工、冲突、超时和未验证项。
3. **提出候选规则**：每条候选规则必须包含“触发条件 → Hermes 动作 → 验收标准”。
4. **筛选**：只有满足任一条件才进入主 Skill：
   - 同类问题至少出现两次；
   - 一次造成了明显风险，如越权、数据风险、工作树冲突或验收错误；
   - 用户明确要求改变团队行为。
5. **最小改动**：优先用精确 patch 修改 `SKILL.md`；避免重写无关章节。
6. **验证新规则**：在下一次匹配任务中检查它是否实际改变了调度或验收行为。
7. **发布版本**：更新 Skill frontmatter 版本、`CHANGELOG.md`，提交并推送。只在验证后再声明规则有效。

## 决策标准

### 候选规则的质量门槛

保留的规则必须同时满足：

- **可触发**：能明确回答“什么时候适用”。
- **可执行**：写出 Hermes 必须做什么，而不是“注意”“尽量”。
- **可验证**：能从 diff、测试、A2A 回复、退出码或任务记录验证。
- **通用**：不是某个仓库的临时细节；仓库特定规则应留在该项目的 `AGENTS.md`、`.hermes.md` 或任务契约中。
- **不重复**：如已有规则覆盖，应补强原规则而非新增近义句。

### 版本规则

- `0.1.x`：小修正、模板增强、澄清既有行为。
- `0.2.0`：新增完整流程模块，例如正式 worktree 策略、测试矩阵或失败恢复状态机。
- `0.3.0`：引入跨任务记忆、任务板、指标或自动化辅助。
- `1.0.0`：在多个不同类型仓库中验证，核心工作流稳定。

## 优先迭代路线

### 阶段 A：证据化交付（建议下一个版本：0.1.1）

目标：消除“Agent 口头完成”的假阳性。

拟加入：

1. peer 最终交付统一格式：状态、修改文件、实际命令、退出码、风险、建议复核点。
2. Hermes 完成门禁：未审查 diff、未取得验收命令的真实结果时，禁止标记任务完成。
3. 高风险变更识别：认证、权限、支付、数据库迁移、并发、安全、删除/迁移数据，必须由未实现的一方只读复核。

验收：至少三个真实任务中，每次都能在最终报告看到命令与实际状态；高风险任务都有独立审查证据。

### 阶段 B：隔离并行（建议版本：0.2.0）

目标：提高并行度但避免写入冲突。

拟加入：

1. worktree 建立、命名、清理与集成检查流程。
2. 文件所有权/目录边界表，决定任务可以并行还是必须串行。
3. 合并顺序与冲突恢复规则。

验收：至少两个并行写入任务在隔离 worktree 中完成；主工作树无未解释冲突，且最终测试通过。

### 阶段 C：角色路由和质量校准（建议版本：0.3.0）

目标：让模型选择基于证据，而不是固定偏好。

拟加入：

1. 任务类型 × peer 表现记录：实现、测试、审查、重构、调研。
2. 以返工率、测试通过率、耗时、超时率和审查发现数作为指标。
3. 基于最近足够样本的路由建议；样本不足时保持当前默认角色分工。

验收：至少十条结构化复盘记录；路由调整可说明具体证据，且不只依据一次成功或失败。

### 阶段 D：持久化协作（可选）

当任务跨多个会话或多个仓库时，再考虑 Hermes Kanban、计划文件或自动化报告。不要为了“多 Agent”而在简单任务上引入任务板。

## 不应进入主 Skill 的内容

- 某个仓库单次故障的目录、依赖版本或测试命令。
- 未实际验证过的“最佳实践”。
- 对模型能力的笼统判断，例如“Claude 更强”或“Codex 更快”。
- 密钥、账号、内部 URL、A2A conversation 的敏感原文。
- 纯粹的任务进度或临时 TODO。

## 每月维护

每累计 5–10 次任务或每月一次：

1. 汇总复盘记录；计算重复故障与指标趋势。
2. 将已验证的候选规则合并到 `SKILL.md`。
3. 删除被新规则覆盖的旧条目，保持主 Skill 紧凑。
4. 更新 changelog、版本号和路线图状态。
5. 用一个中等复杂度真实任务回归验证整个流程。
