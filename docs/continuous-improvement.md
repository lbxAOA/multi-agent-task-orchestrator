# 持续优化机制

本 Skill 是可验证的团队运行手册，不是不断堆叠的提示词。复盘是可选的维护工具，不是每个任务的强制步骤。结构化讨论同样按收益触发，不要求每个任务都启动多个 Agent。

## 优化循环

仅在用户或任务契约明确启用复盘时，或用户明确要求根据历史经验改进时，才记录任务复盘：

1. **收集证据**：保存任务契约、执行通道、任务单、修改范围、验收命令、退出状态和 A2A `context_id`（如有）。
2. **按需记录**：从 `retrospective-template.md` 创建复盘，明确成功、失败、返工、冲突、超时和未验证项。
3. **提出候选规则**：每条规则必须包含“触发条件 → Hermes 动作 → 验收标准”。
4. **筛选**：仅在同类问题至少两次出现、单次造成明显风险，或用户明确要求改变行为时，才写入主 Skill。
5. **最小改动**：优先精确更新 `SKILL.md`，删除被替代的规则，避免重复和无关重写。
6. **验证新规则**：在下一次匹配任务中检查它是否实际改变委派、讨论、调度或验收行为。
7. **版本化**：更新 frontmatter 版本和 `CHANGELOG.md` 后再发布。

未经明确启用，Hermes 不创建复盘文件，也不影响任务完成判定。

## 讨论流程的优化

对每次启用结构化讨论的任务，重点观察：

- 讨论是否被正确触发，还是给小任务增加了无效成本；
- 第一轮是否真正独立，是否存在互相锚定；
- Hermes 是否显式转发了交叉质询材料；
- 定性结论是否先于评分；
- 分数、权重、证据和置信度是否完整；
- 是否进行了必要的敏感性分析和失败预演；
- 最终计划是否能直接转化为有依赖和验收条件的工作包；
- 讨论是否在停止条件前无限循环。

只有实际证据支持的改进才进入主 Skill。

## 候选规则质量门槛

规则必须同时满足：

- **可触发**：明确何时适用。
- **可执行**：说明 Hermes 要做什么，不使用“注意”“尽量”等模糊词。
- **可验证**：能由讨论记录、委派记录、diff、测试或退出码验证。
- **通用**：不把单个仓库的临时目录、依赖版本或命令写进主 Skill。
- **不重复**：已有规则可覆盖时，补强原规则而非新增近义句。

## 版本策略

- `0.4.x`：讨论协议、计划模板、规则澄清和可选复盘机制的小修正。
- `0.5.0`：新增完整流程模块，例如 worktree 生命周期、失败恢复状态机或经过样本验证的路由指标。
- `1.0.0`：在多个不同仓库和任务类型中验证后，核心流程保持稳定。

## 不应进入主 Skill 的内容

- 某个仓库单次故障的目录、依赖版本或测试命令；
- 未实际验证的“最佳实践”；
- 对模型能力的笼统判断；
- 密钥、账号、内部 URL、A2A conversation 的敏感原文；
- 纯粹的任务进度或临时 TODO。

## 维护节奏

每累计 5–10 份按需复盘，或用户明确要求时：汇总重复故障和讨论指标趋势，合并已验证规则，删除被覆盖条目，更新 changelog 和版本，并用一个中等复杂度真实任务回归验证。
